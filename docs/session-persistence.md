# Session persistence: U3a/U3b adapter boundary

U3a/U3b provide a SwiftData adapter for starting, recording, editing, finishing, abandoning, and recovering sessions. It is not composed into app startup or UI (U4). This is local persistence behavior only: no set-entry UI, import/export, migration, or restore policy is added.

## Storage contract

- `SessionSchemaV1` is the initial versioned schema. One `PersistedSession` aggregate row contains identity, schema version, lifecycle/timestamps, and an internal encoded DTO for the immutable snapshot and ordered sets.
- Domain values do not conform to SwiftData or persistence `Codable` types. The private-to-feature DTO has explicit load-mode/unit/side fields; decoding reconstructs validated domain values and checks row/DTO identity and version, snapshot identities and order, set references/order/IDs, units, numeric values, lifecycle, and dates.
- Each adapter owns a `ModelContainer` for its store URL. Every operation creates a fresh `ModelContext`, disables autosave, and fetches/validates the latest durable rows; this avoids long-lived context caches hiding another adapter's committed change. The configuration explicitly sets `cloudKitDatabase: .none`.
- Synchronous `@MainActor` check/mutate/save operations serialize in-process adapter calls. Begin validates all rows before enforcing one active session; session-ID uniqueness is not an active-session upsert mechanism.
- Record/edit/finish/abandon decode the latest durable aggregate, mutate a domain value copy, validate/serialize it, and explicitly save. On save error, the operation rolls back that context and surfaces the error; the previous durable state remains authoritative. Terminal repeats reject with `SessionDomainError.closedSession` and never create another history row. A successfully finished/abandoned session allows a subsequent begin.
- A set replacement must target an existing set and retain its immutable set ID, exercise ID, and order. The replacement value is constructed through the same validating domain initializer as a newly recorded set.
- DTO payload safety bounds are shared by recovery and serialization: at most 1 MiB encoded payload, 10,000 sets, and 1,000 snapshot exercises. Serializer checks domain reconstruction, structure, and encoded byte size before save; oversized data is rejected, never truncated. No arbitrary numeric magnitude cap is introduced. Fetch and stored-data validation errors are not treated as an empty store. There is no delete/recreate recovery path.

## Verification and limits

Synthetic temporary on-disk tests cover edit/reopen, finish/abandon/reopen, terminal rejection, next-session begin, immutable snapshot/history, independent-adapter read/edit/finish/recovery, and preservation of last durable state after injected edit/finish/abandon save failures. Oversized serializer payload rejection uses the same 1 MiB limit as recovery. Existing U3a tests continue to cover begin/set reopen, concurrent begins, unknown identity, malformed DTO rejection, and actual read-only-store write failure. Focused iPhone 17 verification passed 13/0/0 (`build/U3bDevice-focused-20261004-worker-02.xcresult`); full `TrainingAppTests` passed 43/0/0 (`build/U3bDevice-regression-20261004-worker-03.xcresult`); the physical-device build succeeded (`build/U3bDevice-build-20261004-worker-04.log`). The initial focused compile attempt (`build/U3bDevice-red-20261004-worker-01.xcresult`) had a test-fixture scope error and zero tests; it was not behavioral RED. Tests were added after implementation, so the original test-first sequencing requirement was missed and remains unmet. A separate postimplementation regression-sensitivity check temporarily replaced only adapter edit/finish/abandon operations with compilable no-ops: 4 tests failed, 9 passed, 0 skipped, with 0 runtime warnings (`build/U3bDevice-sensitivity-20261004-recovery-01.xcresult`, log `build/U3bDevice-sensitivity-20261004-recovery-01.log`; elapsed 318 seconds). The original implementations were restored immediately. Restored behavior then passed focused tests 13/0/0 (`build/U3bDevice-restored-green-20261004-recovery-02.xcresult`), full `TrainingAppTests` 43/0/0 (`build/U3bDevice-regression-20261004-recovery-03.xcresult`), and physical-device build (`build/U3bDevice-build-20261004-recovery-04.log`, `BUILD SUCCEEDED`). This sensitivity evidence demonstrates test detection only; it is not original preimplementation RED and does not satisfy strict TDD sequencing. These tests establish only exercised save/reopen cases; they do not guarantee crash recovery, filesystem-level atomicity beyond SwiftData's save contract, or cross-process/multi-device locking.

Schema v1 has no predecessor. A migration test now would invent a historical schema and would not test a real migration; add fixtures from an actual shipped prior version when schema v2 is introduced. This schema is not a portable backup/import format.

## Current app boundary and future work

The adapter is not wired to app composition or UI. Future U4 work must provide clear edit/finish/abandon actions, show surfaced persistence errors without implying durability, and recover the last durable session on relaunch. This unit adds no import/export, restore, migration, or schema change. Schema v1 remains the initial schema.

## Privacy and API evidence

The owner accepts ordinary iOS device backups, including enabled iCloud Backup. This app does not sync through CloudKit or another service, and this implementation does not exclude its store from OS backups. Restore/conflict policy, encryption, and key recovery remain U6 decisions. On-device storage therefore may also exist in an owner-enabled system backup.
